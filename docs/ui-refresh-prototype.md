# 界面升级原型与前端架构优化方案

## 1. 设计目标

下一阶段界面升级建议围绕“企业级、低学习成本、高识别效率”展开。当前系统已经覆盖饭票生成、企业微信审批、二维码核销、权限管理和报表导出，前端形态上仍集中在单个 Vue 文件中，桌面后台与移动核销共用一套页面骨架。后续需要把管理后台、饭堂核销端、员工手机端入口做清晰分流，让不同角色进入系统后只看到和当前任务相关的内容。

核心目标：

- 企业级：界面风格克制、信息密度合理、操作路径稳定，适合行政、IT、饭堂人员长期使用。
- 简洁：减少首页解释性文字，突出待处理数据、筛选、核销结果和异常原因。
- 桌面端/移动端分流：桌面端面向管理、查询、配置、报表；移动端面向核销和员工自助余额查询。
- 高可读性：饭堂核销场景以“成功/失败/原因/饭票关键信息”为第一屏核心，颜色、字号和布局优先服务现场判断。
- 可扩展：预留万傲瑞达 6000 平台对接后的“企业微信 UserID 与饭卡账号映射”“饭卡余额查询”“同步状态监控”等界面位置。

## 2. 信息架构

### 2.1 角色与入口分流

建议将前端按访问设备和登录身份分为四类入口：

- 管理后台：桌面端优先，给 `admin`、`hr`、`auditor` 使用。
- 核销端：手机端优先，给 `verifier` 使用，扫码进入后自动展示核销结果。
- 员工中心：企业微信自建应用手机入口，给员工查看饭卡余额、最近饭票和绑定状态。
- 公开票面：保留 `/ticket?token=...` 展示二维码图片或票面图片的能力，避免影响已有消息链路。

推荐路由结构：

```text
/login                     登录页
/admin/dashboard           桌面 Dashboard
/admin/tickets             饭票记录
/admin/tickets/create      饭票生成
/admin/reports             报表中心
/admin/users               用户与权限
/admin/card-mappings       企业微信与饭卡映射
/admin/settings            系统设置
/mobile/verify             移动核销结果页
/mobile/me                 员工中心
/mobile/card-balance       饭卡余额
/ticket                    饭票二维码展示
```

### 2.2 后台菜单重组

当前菜单包括“饭票管理、饭票生成、扫码核销、系统设置、权限管理”。建议升级为更贴近生产系统的分组菜单：

```text
工作台
- 数据概览

饭票业务
- 饭票记录
- 饭票生成
- 核销日志

员工与饭卡
- 用户与权限
- 企业微信用户映射
- 饭卡余额查询
- 万傲瑞达同步记录

报表审计
- 行政核对报表
- 导出任务
- 操作审计

系统配置
- 企业微信配置
- 审批字段映射
- 核销规则
- 票面样式
- 万傲瑞达接口配置
```

菜单应按角色裁剪：

- `admin`：全部菜单。
- `hr`：饭票业务、部分报表、员工映射只读或协助维护。
- `auditor`：数据概览、饭票记录、报表审计。
- `verifier`：默认进入移动核销端，不进入桌面后台菜单。
- 员工：默认进入员工中心，只能查看本人饭卡余额和本人饭票。

### 2.3 用户中心与饭卡余额入口

企业微信自建应用可增加“我的饭卡”入口。用户点击后通过企业微信 OAuth 或 UserID 识别身份，系统根据映射关系查询万傲瑞达 6000 平台饭卡余额。

员工中心建议包含：

- 当前用户：姓名、部门、企业微信 UserID。
- 绑定状态：已绑定饭卡 / 未绑定 / 映射异常。
- 饭卡余额：当前余额、更新时间、数据来源。
- 最近记录：最近饭票、最近消费或同步记录。
- 异常提示：未绑定饭卡时提示联系行政或 IT，不在页面暴露技术错误。

### 2.4 核销端

核销端只保留现场必要信息。扫码后进入 `/mobile/verify?token=...`，如果核销员未登录，先跳转登录；已登录且缓存有效时直接核销并显示结果。

核销端第一屏优先级：

1. 核销结果：成功、失败、已核销、已过期、非当天、餐别时间不符、无权限。
2. 饭票关键信息：餐别、用餐日期、申请人、部门、饭票编号。
3. 操作按钮：继续扫码、返回首页、退出登录。

### 2.5 报表端

报表端建议从“饭票记录导出”升级为“行政核对工作区”：

- 支持按日期、部门、餐别、来源、状态、申请人筛选。
- 显示合计：应核销、已核销、未核销、作废、过期。
- 支持保存常用筛选。
- 支持异步导出任务，避免数据量大时页面等待。
- 支持按企业微信审批单号追踪生成与核销明细。

## 3. 视觉主题建议

### 3.1 色彩

建议使用“浅底中性色 + 稳定主色 + 明确状态色”的企业级主题，避免大面积高饱和渐变。

基础色：

- 页面背景：`#F5F7FA`
- 主内容背景：`#FFFFFF`
- 边框：`#E3E8EF`
- 主文字：`#1F2937`
- 次级文字：`#667085`
- 弱文字：`#98A2B3`

品牌主色建议：

- 主色：`#176B87`，用于主按钮、选中菜单、关键图标。
- 辅助色：`#2A9D8F`，用于成功趋势、轻量提示。
- 强调色：`#F59E0B`，用于待核销、临近异常。

状态色：

- 成功：`#16A34A`
- 失败：`#DC2626`
- 警告：`#D97706`
- 信息：`#2563EB`
- 禁用/作废：`#6B7280`

### 3.2 字体层级

桌面端建议：

- 页面标题：20-22px，字重 650。
- 模块标题：16-18px，字重 600。
- 表格正文：13-14px。
- 辅助说明：12-13px。
- 数字指标：24-30px，使用等宽或紧凑数字样式。

移动端建议：

- 核销结果标题：28-34px，现场一眼可读。
- 失败原因：16-18px，最多两行，重要原因加粗。
- 饭票字段名：12px。
- 饭票字段值：16-18px。

### 3.3 间距与布局

桌面端：

- 左侧菜单宽度 232-248px。
- 顶部栏高度 64px。
- 内容区边距 24px。
- 面板内边距 16-20px。
- 表格行高 44-48px，适合行政快速扫描。
- 筛选区使用单行紧凑布局，窄屏再折行。

移动端：

- 使用 100dvh 全屏布局。
- 顶部只保留当前任务标题和退出/返回按钮。
- 核销结果卡片占第一屏 35%-45% 高度。
- 关键字段使用两列卡片或纵向列表，避免横向滚动。
- 主要操作按钮固定在底部安全区上方。

### 3.4 表格密度

饭票记录表格建议分为“默认视图”和“密集视图”：

- 默认视图：适合普通行政核对，展示饭票编号、申请人、部门、餐别、用餐日期、状态、核销时间、来源。
- 密集视图：适合批量核查，减小行高，隐藏非必要列。
- 重要列固定：饭票编号、申请人、状态、操作。
- 长文本列使用 tooltip，但筛选结果中应尽量保留部门和审批单号。

### 3.5 移动端全屏核销风格

核销成功页建议使用绿色顶部结果区，失败页使用红色顶部结果区，避免只依赖小标签判断。

```text
+--------------------------------+
| 核销成功                         |
| 午餐 · 今日有效                   |
+--------------------------------+
| 申请人      张三                  |
| 部门        行政部                |
| 用餐日期    2026-06-05            |
| 饭票编号    MT202606050001        |
+--------------------------------+
|          继续扫码                |
+--------------------------------+
```

失败页需要直接显示原因：

```text
+--------------------------------+
| 核销失败                         |
| 当前时间不在午餐核销时间段内       |
+--------------------------------+
| 允许时间    11:00-13:30           |
| 当前时间    15:42                 |
| 饭票状态    未使用                |
+--------------------------------+
|          继续扫码                |
+--------------------------------+
```

## 5. 前端架构优化建议

### 5.1 从单文件应用拆分为页面与组件

当前 `frontend/src/main.js` 同时承载状态、接口、权限、模板和页面布局。下一阶段建议逐步拆分，不一次性大改。

建议目录：

```text
frontend/src/
  app/
    router.js
    permissions.js
    api.js
  layouts/
    AdminLayout.vue
    MobileLayout.vue
    PublicTicketLayout.vue
  pages/
    LoginPage.vue
    admin/
      DashboardPage.vue
      TicketListPage.vue
      TicketCreatePage.vue
      UserManagementPage.vue
      CardMappingPage.vue
      ReportPage.vue
      SettingsPage.vue
    mobile/
      VerifyPage.vue
      BalancePage.vue
      EmployeeHomePage.vue
  components/
    tickets/
    users/
    settings/
    mobile/
    common/
  styles/
    tokens.css
    admin.css
    mobile.css
```

### 5.2 状态与接口分层

建议把接口调用集中到 `api` 目录：

```text
api/auth.js
api/tickets.js
api/settings.js
api/users.js
api/cardMappings.js
api/reports.js
```

可复用状态建议：

- 当前用户与权限：`useAuthStore`。
- 饭票筛选条件：页面本地状态即可。
- 系统设置：`useSettingsStore`，保存后刷新缓存。
- 移动端登录缓存：保留一天有效期，过期后重新登录。

如果后续继续使用 Vue 3，建议引入 `vue-router` 和 `pinia`，Element Plus 保留作为桌面端组件库。移动端可以继续用原生 CSS 实现，避免额外引入过重移动端组件库；如要引入，可评估 Vant，但要注意与 Element Plus 的视觉一致性。

### 5.3 样式系统

建议先建立 CSS Token，再重构页面样式：

```css
:root {
  --color-bg: #f5f7fa;
  --color-surface: #ffffff;
  --color-border: #e3e8ef;
  --color-primary: #176b87;
  --color-success: #16a34a;
  --color-danger: #dc2626;
  --space-1: 4px;
  --space-2: 8px;
  --space-3: 12px;
  --space-4: 16px;
  --space-6: 24px;
}
```

桌面端和移动端样式建议拆开：

- `admin.css`：侧栏、顶部栏、面板、表格、筛选区。
- `mobile.css`：全屏核销、员工中心、余额卡片。
- `tokens.css`：颜色、字号、间距、阴影、圆角。

## 6. 分阶段实施建议

### 阶段一：低风险样式重构

目标：不改接口，不大拆文件，先提升可用性和观感。

建议任务：

- 增加 CSS Token，统一颜色、间距、圆角和状态色。
- 修正桌面端标题、筛选区、表格和按钮对齐。
- 优化移动端核销页为全屏结果布局。
- 登录页增加清晰错误提示和生产环境默认账号提示策略。
- 饭票记录增加状态 Tab、列密度优化和批量操作条。

验收标准：

- 桌面端 1440px、1280px、1024px 不出现内容挤压。
- 手机端 390px、430px 第一屏能完整显示核销结果和关键字段。
- 成功、失败、重复核销、过期、非当天、餐别时间不符均有明确颜色和原因。

### 阶段二：拆分 Vue 单文件

目标：降低维护成本，为万傲瑞达对接和员工中心做空间。

建议任务：

- 引入 `vue-router`。
- 拆出 `AdminLayout`、`MobileLayout`、`LoginPage`。
- 将饭票记录、饭票生成、系统设置、用户权限拆为独立页面。
- 将接口调用从 `main.js` 抽离到 `api` 模块。
- 将权限判断抽离成 `permissions.js` 或组合式函数。

验收标准：

- 现有功能行为不变。
- 原 `/verify?token=...` 或新 `/mobile/verify?token=...` 链路可兼容旧二维码。
- 角色菜单显示与当前权限保持一致。

### 阶段三：补组件化与新业务页面

目标：接入万傲瑞达 6000 平台后的页面可维护、可扩展。

建议任务：

- 新增“企业微信用户映射”页面。
- 新增“饭卡余额查询”后台页面。
- 新增员工移动端“我的饭卡”页面。
- 新增“万傲瑞达同步记录”页面。
- 抽象 `StatusTag`、`MetricCard`、`FilterBar`、`DataTableToolbar`、`MobileResultHero` 等组件。
- 增加前端 smoke test 或 Playwright 关键页面截图检查。

验收标准：

- 管理员可以维护 UserID 与饭卡账号映射。
- 员工从企业微信进入后只看到本人余额。
- 万傲瑞达接口异常时后台可追踪，员工端提示友好。
- 核销端仍保持一屏可读，不被新增业务干扰。

## 7. 优先级建议

短期优先做：

1. 移动核销结果页全屏化和失败原因强化。
2. 桌面后台菜单重组和饭票记录表格优化。
3. 系统设置拆 Tab，降低配置页面复杂度。
4. 新增用户映射页面原型，为万傲瑞达对接准备数据入口。

中期再做：

1. 拆分 `frontend/src/main.js`。
2. 引入路由和状态管理。
3. 员工中心与饭卡余额移动入口。
4. 报表中心和同步监控。

长期建议：

1. 建立前端设计 token 和组件规范。
2. 增加页面级自动化截图验收。
3. 将万傲瑞达接口配置、同步任务、错误告警纳入运维后台。
